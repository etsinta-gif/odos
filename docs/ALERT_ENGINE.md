# ODOS Alert Engine

## Overview

INTEL-3 adds an Automation, Alerts, and Notifications layer on top of red flags generated by the ETL intelligence flow.

## Key Concepts

### Alert Rules
- Conditions determine when a rule triggers on a red flag.
- Actions define what executes after trigger (email, webhook, in-app, auto-resolve, auto-assign).
- Priority drives assignment and escalation behavior.

### Escalation Policies
- Policy levels define escalation windows and optional role targets.
- Open red flags exceeding configured windows are escalated.
- Escalations generate audit entries and optional in-app notices.

### Notifications
- Email notifications are sent using SMTP environment settings.
- Webhook notifications POST payloads to configured URLs.
- In-app notifications are persisted in `alert_notifications` and can be marked read.

### Automated Actions
- Auto-resolve resolves open INFO red flags.
- Auto-assign selects role-based users for high-priority routing and logs assignment actions.

### Audit Trail
- All rule triggers, escalation actions, and status transitions are written to `alert_audit_logs`.

## Workflow

1. Red flag is created by ETL verification.
2. Rule engine evaluates active matching rules.
3. Configured actions run for triggered rules.
4. Notification events and outcomes are stored.
5. Escalation engine reviews overdue open flags.
6. Automation engine performs periodic low-severity closure.

## API Endpoints

### Red Flags
- `GET /api/alerts/red-flags`
- `GET /api/alerts/red-flags/summary`
- `PUT /api/alerts/red-flags/{id}/resolve`
- `PUT /api/alerts/red-flags/{id}/ignore`

### Rules

- `GET /api/alerts/rules/{id}`
- `POST /api/alerts/rules`

- `DELETE /api/alerts/rules/{id}`
- `POST /api/alerts/rules/{id}/test`
- `POST /api/alerts/red-flags/{id}/evaluate`

### Escalation
- `GET /api/alerts/escalation-policies`
- `POST /api/alerts/escalation-policies`

### Notifications and Audit
- `GET /api/alerts/notifications`
- `PUT /api/alerts/notifications/{id}/read`
- `GET /api/alerts/audit`

### Automation and Scheduler
- `POST /api/alerts/automation/auto-resolve`
- `POST /api/alerts/scheduler/run-once`

## Scheduler Configuration

Scheduler startup is controlled by environment variable:
- `ALERT_SCHEDULER_ENABLED=1` to enable background loop.

Intervals (seconds):
- `ALERT_SCHEDULER_RULE_INTERVAL_SEC` (default 300)
- `ALERT_SCHEDULER_ESCALATION_INTERVAL_SEC` (default 1800)
- `ALERT_SCHEDULER_AUTO_RESOLVE_INTERVAL_SEC` (default 3600)

## Email Configuration

- `EMAIL_HOST`
- `EMAIL_PORT` (default `587`)
- `EMAIL_FROM`
- `EMAIL_USERNAME` (optional)
- `EMAIL_PASSWORD` (optional)
- `EMAIL_USE_TLS` (`1` by default)

If SMTP is not configured, email delivery is logged as failed in notifications without crashing rule execution.
